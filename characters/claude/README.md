# Claude

A pixel-art Claude character: a flat three-colour creature in terracotta `#CC785C`,
with two solid black rectangular eyes, two side ear-nubs and four stubby legs. It uses
the `base-patch` layout, the same as Copilot.

All 13 tracks are **rendered** from a box model of the pixel art, not generated by an
image model. The renderer needs no API key, and every pose is registered by
construction.

## Regenerating

```bash
python3 characters/claude/tools/render_claude_sheet.py --all --expressions --cells  # 1,560 cells, a few minutes
python3 characters/claude/tools/build_claude_animation.py   # merged sprites/animation.json
python3 characters/claude/tools/build_claude_previews.py    # preview/ contact sheets
python3 characters/claude/tools/export_frames.py            # frames.bin + frames.json
python3 tools/character_pack.py build                       # build/characters/claude.acpk
npm run character claude                                    # install over USB or Wi-Fi
```

All five steps are deterministic. CI re-runs the export and fails if `frames.bin` or
`frames.json` would change. The pack builder runs `validate_frames.py`, which refuses a
`frames.bin` that no longer matches the committed cells. It uses only the standard
library, because daemon setup builds packs with a plain `python3`; the renderer and
exporter need `requirements-art.txt`.

## What is here

| Path | What it is |
| --- | --- |
| `sprites/` | **The art.** 13 tracks x 24 poses x 5 blink levels (1,560 cells of 240x224), a manifest per track, and the merged `animation.json` everything downstream reads. |
| `frames.bin`, `frames.json` | The exported pack payload and its frame table. |
| `preview/` | One contact sheet per track, built from `sprites/`, so a preview cannot drift from the art. |
| `source/source-graphic.png` | The supplied artwork, unmodified: 253x198, flat three-colour, cropped flush to the silhouette. |
| `source/reference.png`, `reference-cell.png` | The character redrawn crisply on pure black, at 2x and exact cell scale. |
| `tools/create_claude_reference.py` | Redraws the references from measured geometry. |
| `tools/render_claude_pose.py` | Renders the creature as a rigid box model at any yaw and pitch. |
| `tools/render_claude_sheet.py` | Renders every track's 24 poses and 5 blink levels straight to registered cells. |
| `tools/build_claude_animation.py`, `build_claude_previews.py` | The merged manifest and the contact sheets. |
| `tools/export_frames.py` | The base-patch exporter. |
| `tools/validate_frames.py` | The pack builder's check that `frames.bin` still matches `sprites/`. |

The geometry is a 23px grid measured from `source-graphic.png`: a body 9 units wide,
1-unit eyes inset 1 unit from each edge, 1-unit ear-nubs, and legs on units 0, 2, 6
and 8. The references are redrawn rather than rescaled, which keeps the hard edges the
character is made of.

## Why rendered, not generated

The image model was tried first, with a reference image, per-pose prompts and layout
guides, the way Copilot was made. It handled the four cardinal turns acceptably but could
not hold the diagonals. Across eight diagonal generations it hung the legs off the back
face or the front face, lost them entirely, or rolled the body 75 degrees where 22 was
correct. A character built entirely from axis-aligned boxes is exactly the case for a
model rather than an image API.

The expressions are rendered too. Mixing generated expressions with rendered idle tracks
would put a shading seam at frame 0, which the motion engine passes through on every
transition.

Three things in the renderer exist to close the surface gap against generated art. Read
this before "fixing" them:

- **`CAMERA_LIFT`** is a small constant downward camera tilt. A generated turn reveals
  the creature's top face as it rotates, which a level camera never would under pure
  yaw. Making it proportional to yaw was tried first; a pitch that grows with yaw grows
  the silhouette too, which reintroduced the height drift the renderer exists to avoid.
- **Lambert shading** off a fixed light, normalised so the resting front face is exactly
  the reference colour.
- **3x supersampling.** This character is all hard edges, and aliasing on a 240x224 cell
  was most of what made early procedural frames read as crude.

Eye boxes come off the model through the same per-pixel z-buffer, so occlusion is exact:
zero eyes means genuinely hidden, not undetected.

## Invariants

All 312 poses, checked after every render:

| Invariant | Value |
| --- | --- |
| Frame 0 byte-identical across all 13 tracks | yes |
| `surprise` ends on that same centre pose | yes, all 5 blink levels |
| Eye boxes per pose | exactly 2, 312/312 |
| `up`/`down` width drift | 0px (pitch leaves width fixed) |
| Worst cell padding | 11px |
| Resting body colour | exactly `#CC785C` |

The exporter enforces the first two, and both are cheap to break. `complete` once used
constant eye multipliers instead of ramping them from 1.0, so its frame 0 started with
oversized eyes. `surprise` needs a spring curve (`sin(pi * t**0.7)`), not a linear ramp,
or it ends stuck wide-eyed at the hand-off back to idle. The `complete` chevron's middle
block must overlap the outer blocks (a rise of 0.35 of the eye height, not 0.5), or the
eye reads as a cross rather than one arc.

## Blinks

Blink levels are `[1, 0.75, 0.5, 0.25, 0]`, written as `<track>-<NN>-blink-<1..4>.png`.
The usual blink-synthesis problems (an eyelid colour sampled from a bloom-tinted halo, a
paint mask too tight to cover a glow's outer ring, an edge erosion that clips the
feature) all come from painting over a glow. These eyes are flat black on flat
terracotta and are re-rendered at each openness, so none of that applies. The lower lid
stays put and the upper edge descends. A fully closed eye keeps a thin line: on flat art,
an eye that vanishes reads as a blank face.

The largest blink patch is an 84x56 rectangle, **4,704 px**, on `down_right-23-blink-4`,
under Copilot's 7,452 px. Measure it across every track, not one: the `right` track alone
peaks at 2,464 px, because a pitched, yawed pose spreads the two eyes apart in both axes
and the patch is the single rectangle enclosing both.

## Lessons from the image-model attempts

Worth knowing before trying an image model on any rigid character:

- **A front-on reference carries no depth, and prompt text cannot supply it.** The first
  sheet drew the body as a flat card, with an implied depth of 4.6% where the prompt asked
  for 67%. Restating the depth several ways changed nothing (6.2%). *Showing* the model the
  solid did: pinning rendered poses into the layout guide lifted it to 31%.
- **The model reproduces a pinned pose but re-scales it anyway.** Five pinned cells of a
  constant 160px came back 155 to 169px. Pinning fixes geometry, not scale, and more pins
  barely help.
- **Pinning costs surface quality.** By 5 of 24 cells the output had started converging
  on the pinned renders' flat shading, which spends the only advantage the image model had.
- **Verify sign conventions by rendering, never by reading the code.** In
  `render_claude_pose.py` negative pitch looks up. An early track table had this inverted,
  which would have produced six backwards tracks that looked internally consistent.

## Character-specific gotchas

- **The eyes are pure black, and so is the background.** Glow-based eye detection
  inherited from other characters finds nothing. Detect the darkest regions enclosed by
  the hole-filled silhouette, windowed to its upper 55%, or the gaps between the four
  legs register as extra eyes.
- **Aspect filters from other characters reject every detection.** These eyes go from
  18px wide front-on to 3px at 69 degrees of yaw.
- **The silhouette is not a bust.** The rotation pivot is the centre of the body block,
  20px above the cell centre, because of the legs.
- **Renderers need a per-pixel z-buffer.** Face-average depth sorting dropped the eyes
  and turned the near ear-nub into a sliver. Faces are wound so a camera-facing one has
  negative shoelace area in this Y-up frame; culling the wrong sign renders the inside of
  the box.
